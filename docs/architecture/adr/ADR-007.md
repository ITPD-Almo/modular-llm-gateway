# ADR-007: Store Gateway Usage Events In A Separate Analytics Backend

- **Status:** Accepted
- **Created:** 2026-11-08
- **Updated:** 2026-11-08
- **Containers:** `gateway`
- **Addresses:** [FR-012](../../functional-requirements/fr/FR-012.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

The analyst needs to see whether a private trial completes a configured-plugin chat and identify where attempts stop. The gateway can observe the whole core task without an identity cookie, external provider account or raw message storage.

## Considered Options

- **Dedicated self-hosted OpenObserve for analytics:** one service supports JSON event ingestion, SQL metrics, and a raw event panel with a separate data volume and credentials.
- **OpenPanel:** the course default offers product-focused reporting. It adds a different deployment stack for this small SQL-defined funnel.
- **Combine analytics and operational logs in one scope:** mixes purposes and makes smoke isolation and reader access harder to verify.

## Decision Outcome

Use a dedicated OpenObserve instance for analytics, separate from the observability instance. The parent gateway exports allowlisted JSON batches into one organization per environment. The bounded queue keeps backend calls outside request handling. The [analytics plan](../../analytics.md) owns the event schema and queries. The backend is an external system even when the team self-hosts it.

## Consequences

- **Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** fixed fields, opaque runtime identifiers and scoped credentials restrict the exported information.
- **Operational cost:** analysts get one maintained SQL definition and consistent staging and production panels. The operator maintains a second instance and separate retention and credentials.
- **Delivery tradeoff:** events can be lost when the backend is unavailable or the queue is full. The gateway keeps serving and reports the measured events rather than claiming complete traffic coverage.
