# ADR-004: Emit Allowlisted Lifecycle Events In The Parent

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `gateway`
- **Addresses:** [FR-008](../../functional-requirements/fr/FR-008.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-03](../../quality-requirements/qr/QR-03.md)

## Context

An operator needs to identify a failed plugin and stage without receiving raw prompt content, metadata or an exception message.
A stalled or abruptly exiting worker must not be the only source of its own failure record.
Independent review agreed the diagnostic design alongside the supervisor; it provides operating events rather than durable compliance records.

## Considered Options

- **Parent-generated structured events from a bounded worker protocol:** validate fixed control messages and create event JSON in the supervising application.
- **Forward arbitrary worker logs and tracebacks:** rejected because they can include request content, credentials and exception text, and cannot reliably represent a worker killed mid-hook.
- **Return only a generic HTTP 500:** rejected because it leaves the operator unable to identify which configured hook failed.
- **Add a durable log database now:** deferred because retention, access and storage belong to an operator's deployment, beyond this increment's diagnostic boundary.

## Decision Outcome

Chosen option: emit one JSON lifecycle record per start and terminal outcome through `gateway.plugin_events`, using configured logging handlers or stderr by default.
Only `schema_version`, `event`, `request_id`, `plugin`, `stage`, `elapsed_ms` and `reason` enter the event object.
The parent derives the plugin identity from configured classes and accepts only fixed stage/event/reason values; it does not copy worker-supplied payloads or exception strings into diagnostics.
Generate the request correlation identifier in the gateway, ignore a client-supplied identifier and return it as `X-Request-ID` for the documented handled chat outcomes.
A failed request hook prevents later hooks; a timeout and an unreaped-worker outcome are emitted by the supervisor using the same schema.
Discard worker stdout/stderr. The parent startup/import boundary and any plugin-managed external side effects remain trusted and outside the lifecycle event contract.

## Consequences

- **Security / Confidentiality — [QR-03](../../quality-requirements/qr/QR-03.md):** fixed fields and reason codes exclude raw content from gateway-generated events and handled errors. Correlation identifiers remain operational data: operator access and retention still matter. This is not a promise about arbitrary side effects of trusted Python plugins.
- **Maintainability / Testability — [QR-01](../../quality-requirements/qr/QR-01.md):** synthetic secret fixtures can fail the schema/privacy contract, and a single event shape covers normal, failed and timed-out hooks; a new reason or schema version requires a corresponding check and guide update.
- **Cost:** allowlisting sacrifices arbitrary traceback detail. Local stderr provides neither durable delivery nor storage, rotation, tamper resistance or a retention policy; operators must configure a suitable sink.
- **Agreement:** independent review reproduced the safe event/error boundary, including correlated validation errors, and agreed this choice. No Customer story approval is inferred from technical logs.
