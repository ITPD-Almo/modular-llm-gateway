# ADR-003: Supervise Each Request In A Disposable Worker

- **Status:** Proposed
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `gateway`
- **Addresses:** [FR-006](../../functional-requirements/fr/FR-006.md), [FR-007](../../functional-requirements/fr/FR-007.md), [QR-01](../../quality-requirements/qr/QR-01.md), [QR-02](../../quality-requirements/qr/QR-02.md)

## Context

A sleeping or CPU-bound synchronous hook can exhaust the baseline request thread pool; returning a timeout from a waiting thread does not stop that hook.
The requirement is a bounded, named outcome and later healthy work, not merely a client deadline.
The implementation draft proposes 250 ms per hook and HTTP 504 for a timeout. Those numbers and the fail-request policy are team proposals awaiting Customer validation; this proposed record still needs independent team agreement.

## Considered Options

- **Disposable spawned worker for the complete request pipeline:** each admitted request owns one process, with plugin instances shared between its two stages and then discarded.
- **Thread pool plus a wait timeout:** rejected because Python cannot safely terminate an arbitrary running thread; repeated timeouts keep consuming resources.
- **Cooperative async cancellation:** rejected for arbitrary synchronous hooks because a blocking or CPU-bound hook need not yield to cancellation.
- **One persistent worker pool:** deferred because restarting wedged workers and recovering request/response instance ownership adds state management; it may later reduce spawn cost if measured overhead warrants it.
- **Skip the failed hook and continue:** rejected as the proposed default because bypassing a transformation may change policy behavior. Confirm the policy with the Customer rather than treating rejection as their verdict.

## Decision Outcome

Chosen option for review: one bounded disposable spawned worker per request, running request hooks, the internal provider and response hooks under a parent supervisor.
The proposed defaults are 250 ms per hook, four concurrent managed workers per application process, a 1000 ms worker-start/IPC budget, a one-MiB encoded JSON limit and 100 ms per cleanup join.
The parent terminates an over-budget worker, joins it, escalates to kill if needed and joins again. An unreaped worker retains its admission slot until reaped; admission never creates unlimited unmanaged workers.
Timeout returns a named HTTP 504; exhausted admission returns 503; hook exceptions and invalid outputs return named 500; provider failure returns 502; an oversized encoded request returns 413.
A request-stage failure prevents the provider call. A response-stage failure stops remaining response hooks and discards the reply; it cannot undo the provider call or external side effects.
Each request gets fresh plugin instances. Its request/response hooks share those instances; plugins must not rely on mutable instance state surviving a later request.
Configuration paths are frozen at application creation until restart.

## Consequences

- **Reliability / Fault Tolerance — [QR-02](../../quality-requirements/qr/QR-02.md):** terminating and reaping a managed worker bounds ongoing hook work rather than abandoning a thread. Bounded slots limit repeated failure accumulation, but process creation and IPC add overhead; the one-second synthetic target requires measurement on the deployment and is not a hard real-time OS guarantee.
- **Maintainability / Testability — [QR-01](../../quality-requirements/qr/QR-01.md):** tests must exercise actual spawn, both stages, repeated timeouts, cleanup, capacity, malformed output and the changed instance lifetime. A mocked deadline alone is insufficient.
- **Cost:** the initial application-factory import/construction validation remains trusted startup work outside hook deadlines; a hanging initial constructor can still prevent startup. Worker-side initialization has a separate bound.
- **Cost:** worker separation is not a security sandbox or a rollback mechanism. Arbitrary external subprocess descendants and external side effects are unsupported. Per-request spawn and the payload limit constrain plugin compatibility; cross-request state must be designed elsewhere if later required.
- **Status:** keep this record Proposed until the independent reviewer agrees the lifecycle, failure policy and limits. Acceptance by the team does not create a Customer story verdict.
