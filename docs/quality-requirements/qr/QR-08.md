# QR-08: Diagnose A Failed Chat From Its Operating Signals

An operator can locate a failed configured-plugin chat and see its failure-series latency in the staging observability organization.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

The system operator investigates a failed request.

### Stimulus

A chat in the core task reaches the configured slow request hook and returns a named HTTP 504.

### Environment

Staging on the university VM, with a reachable staging observability organization, the staging fake provider and the slow-plugin fixture. The operator queries from the university network.

### Artifact

The gateway chat path, its exported structured request point and the [SLI-01 histogram](../../observability.md#sli-01).

### Response

The organization exposes the failed request's log point by request ID and a numeric five-minute P95 in the separate timeout series.

### Response Measure

Within five seconds of the failed response, the staging organization's query returns exactly one log point carrying its request ID, route, failure outcome and duration. Within one minute, the same organization's SLI-01 query returns a numeric P95 for the timeout series.

## QRT-01

Send normal and deliberately failing chat requests, then query both signals in the staging organization.

- **Status:** Active
- **Level:** deployed
- **Runs at:** staging university VM deployment from a campus client using `$STAGING_URL` and `$OPENOBSERVE_URL`, reading [SLI-01](../../observability.md#sli-01).

### Procedure

1. Record the full staging commit and prepare the fake provider and slow-plugin fixture using the [deployment runbook](../../deployment.md#telemetry-pipelines). Check the organization, exporter intervals and campus route. Keep other synthetic tests out of the measurement window.
2. Run [check-sli.py](../../deployment-tools/check-sli.py) with its staging-only private settings. It checks health, runs two healthy configured chats, records the latest timeout histogram sample timestamp, triggers the named 504 and captures its `X-Request-ID`.
3. The script polls the log query for at most five seconds after the failed response and the aggregate query for at most one minute. It requires a new histogram observation and the matching timeout-series P95. Preserve the sanitized result, staging screenshot, runner, date, network and commit. Restore staging's normal provider and plugin configuration afterward.

**Pass when:** the expected named HTTP 504 returns a request ID, exactly one matching staging log point with the required labels appears within five seconds, and the five-minute SLI-01 query returns a finite numeric P95 for a new timeout observation within one minute.
