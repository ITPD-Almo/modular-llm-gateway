# QR-05: Keep Concurrent Chat Load Bounded And Recoverable

At the default capacity, four concurrent healthy chat requests succeed, and excess concurrent traffic receives a bounded result while health and later requests remain available.

- **Status:** Active
- **Characteristic:** Performance Efficiency
- **Sub-characteristic:** Capacity
- **Business importance:** Medium
- **Technical risk:** Medium

## Scenario

### Source

An operator or a client sending concurrent synthetic chat requests.

### Stimulus

Four healthy requests arrive together, followed by separate bursts of eight and twenty healthy requests.

### Environment

One gateway application process with its default capacity of four concurrent requests, default example plugins and fake provider, with no other traffic or real provider key.
These capacity and time limits are team proposals, not a Customer acceptance verdict.

### Artifact

The gateway's chat and health HTTP interfaces.

### Response

The gateway completes admitted healthy requests correctly and rejects requests arriving at full capacity with HTTP 503 instead of retaining an unbounded backlog.
Health and subsequent healthy requests remain available.
Healthy traffic above the default capacity may be rejected; this is an explicit limit, not a promise that all eight or twenty requests succeed.

### Response Measure

All four requests in the four-request burst return HTTP 200 with the expected synthetic reply.
For each eight- and twenty-request burst, at least four requests return the correct HTTP 200 reply, every other response is HTTP 200 or 503, and every response arrives within two seconds on the tested environment.
A health request during each burst returns HTTP 200 within one second, and ten following nonconcurrent healthy requests all return the correct HTTP 200 reply.
