# FR-010: Verify And Restore A Deployed Release

- **Status:** Active
- **Traces to:** [`US-06`](https://github.com/ITPD-Almo/modular-llm-gateway/issues/66), [`CON-04`](../../product-vision.md#con-04)
- **Containers:** `gateway`
- **Changed:** 2026-10-25: fixed the recovery environment, deadline and known-good identity checks for future backlog refinement.

## Behavior

After each deployment, the product shall run normal-order, changed-order, plugin-error and timeout-recovery smoke checks against the deployed endpoint and mark the deployment failed when any check fails.

When a deployment fails its checks, the product shall allow the operator to restore the previous known-good artifact and configuration by the documented procedure.

The previous artifact and matching configuration shall remain available locally on the operator-provided host until its successor passes the checks.
For a failed synthetic deployment with no persistent user data, restoration and all checks shall complete within five minutes of the operator starting the documented restore command.

Implementation status: future target depending on [FR-009](FR-009.md), with the boundary selected in [ADR-005](../../architecture/adr/ADR-005.md) and the recovery scenario in [QR-06](../../quality-requirements/qr/QR-06.md). No hosted deployment or recovery result is claimed yet.

## Acceptance Criteria

### AC-01

Given a deliberately broken deployment, when its smoke checks run, then at least one check fails and the deployment is not reported healthy.

### AC-02

Given a failed deployment and locally retained known-good artifact/configuration, when the operator follows the restore procedure, then within five minutes the endpoint reports their previous identities and all smoke checks pass without a real provider key.

### AC-03

Given an attempted deployment whose checks fail, when its workflow result and operator output are inspected, then neither reports the failed version as healthy or accepted and the failed checks identify the scenario to repeat.
