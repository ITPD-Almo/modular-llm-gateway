# FR-006: Name The Plugin That Failed A Request

- **Status:** Active
- **Traces to:** [`US-02`](https://github.com/ITPD-Almo/modular-llm-gateway/issues/41), [`US-04`](https://github.com/ITPD-Almo/modular-llm-gateway/issues/52), [`CON-04`](../../product-vision.md#con-04)
- **Containers:** `gateway`

## Behavior

When a plugin hook raises an exception, the gateway shall stop processing that request, call no later hook for it, and return HTTP 500 with a detail naming the plugin class and the stage, without the exception text and without a successful reply.

When the failing hook is a request hook, the gateway shall not call the provider for that request.

When a plugin hook returns something other than a dictionary, the gateway shall treat it as a failure of that plugin at that stage in the same way.

After a failed request, the gateway shall keep serving later requests.

Implementation status: the raised-exception case is implemented in [v0.1.0](https://github.com/ITPD-Almo/modular-llm-gateway/releases/tag/v0.1.0). The non-dictionary case is target behavior: [v0.1.0](https://github.com/ITPD-Almo/modular-llm-gateway/releases/tag/v0.1.0) reports it as a provider failure (502) or as an unnamed 500.

## Acceptance Criteria

### AC-01

Given a request hook that raises an error whose text is `secret-xyz`, when a request is sent, then the status is 500, the detail is `plugin FailingPlugin failed during request processing`, the body does not contain `secret-xyz` and the provider is not called.

### AC-02

Given a response hook that raises an error, when a request is sent, then the status is 500 and the detail names the plugin and `response processing`.

### AC-03

Given a request hook that returns `None`, when a request is sent, then the status is 500 and the detail names that plugin and `request processing`, not `provider failed`.

### AC-04

Given any of the failures above, when a request is next sent through healthy plugins only, then it returns 200 with the correct reply.
